# Як дані проходять через шари

```
текст програми
   │  lexer.tokenize            Token(kind, value, span)
   ▼
токени
   │  parser.Parser.program     рекурсивний спуск, одна функція на метазмінну
   ▼
дерево виводу (ParseNode)  ───► visualization.tree: text / json / dot / svg
   │  parser.to_ast             викидаю дужки, ключові слова, ';'
   ▼
AST (ast.Node, кожен зі span)
   ├──► interpreter.run                    стан -> кінцевий стан (+ траса подій)
   └──► semantics.build_term               правила NS_* -> Term
              │
              ▼
          семантичний терм ──► semantics.evaluate   стан -> стан або ⊥ + траса AF_*
```

Кожен шар бере тільки результат попереднього, тому CLI, тести і будь-який інший
інструмент (наприклад, розширення VS Code) можуть брати потрібний шар окремо.

## Лексер (`lexer.py`)

Іде по тексту символ за символом і збирає токени: числа, імена, ключові слова,
оператори (`:=` перевіряється раніше за `:` і `=`). Рахує рядок і колонку, тому
кожен токен має `SourceSpan`. Незнайомий символ - одразу `SiplSyntaxError` з позицією.

## Парсер (`parser.py`)

Рекурсивний спуск. Для кожної метазмінної є функція:

| функція | що розбирає |
|---------|-------------|
| `program` | `begin <оператор> end` |
| `statements` | `S1 ; S2 ; ...`, збирає зліва направо: `(S1; S2); S3` |
| `statement` | присвоєння, if, while, begin-end, skip |
| `aexpr` / `term` / `factor` | `+ -` / `* div mod` / число, змінна, дужки |
| `bexpr` / `bterm` / `bfactor` | `or` / `and` / `not`, true, false, порівняння, дужки |

Пріоритети задаються тим, яка функція викликає яку: `aexpr` викликає `term`, тому
множення «глибше» і рахується раніше. Тіло `while` і гілки `if` розбираються функцією
`statement`, а не `statements`, тому `;` до них не входить.

Єдине місце з поверненням назад - дужка в умові: `(x + 1) > 2` і `(x > 1) and ...`
починаються однаково, тому спершу пробую розібрати порівняння, а якщо не вийшло -
умову в дужках.

Парсер будує дерево виводу (`ParseNode`): внутрішні вузли - метазмінні з назвою правила
(`S_Seq`, `A_Add`, ...), листки - токени. `to_ast` перетворює його на AST.

## Інтерпретатор (`interpreter.py`)

Стан - словник. Присвоєння не змінює старий стан, а робить новий `{**st, x: v}`,
так само як `st ∇ [x ↦ v]`. Кожен оператор рахується як крок, після `max_steps`
кроків виконання зупиняється з помилкою (захист від нескінченного циклу).

## Семантичний терм (`semantics/build.py`)

Функція `build` - пряма реалізація правил NS_*: одна гілка `if` на кожен вид вузла AST,
діти перетворюються рекурсивно. Наприклад, для `while b do S`:
`WH(build(b), build(S))`.

`explain` робить те саме, але вкладені `if` і `while` спочатку записує як `sem_S(...)`
і розкриває їх наступними кроками, як ми писали в практичній 2.

## Обчислення терму (`semantics/evaluate.py`)

Рахує саме терм, а не AST, за правилами AF_*. Для виразу будується ланцюжок рівностей:
`S^2(gr, N⇒, 1̅)(st) = gr(N⇒(st), 1̅(st)) = gr(3, 1) = true`, тобто спочатку AF_S розкриває
суперпозицію, потім AF_DNM підставляє значення змінних, потім рахуються функції від
найглибших до зовнішньої. Для операторів - AF_SEQ, AF_AS, AF_IF, AF_ID, AF_WH; кожен
новий стан отримує ім'я st₁, st₂, ...

Невизначеність (⊥): змінної немає в стані, `div`/`mod` на 0, або цикл не завершився
за `max_iterations` ітерацій.

## JSON-контракти

- `sipl parse --json`: `{"ok": true, "ast": {"node": "Program", "span": {...}, "body": {...}}}`
- `sipl tree -f json`: `{"symbol", "rule", "bnf", "span", "text", "children" | "leaf"}`
- `sipl term --json`: `{"ok", "term", "tree": {"term": "Comp", ...}, "steps"?}`
- `sipl eval --json`: `{"ok", "defined", "initial", "state", "undefined", "steps": [{"kind", "rules", "text"}]}`
- помилка: `{"ok": false, "error": {"kind": "syntax"|"runtime"|"error", "message", "span"}}`

`span`: `{"line", "col", "end_line", "end_col"}`, рахунок з 1, кінець не включно.
